# React Code Style
按下面规则生成 React 代码；如果项目现有写法与本 skill 不冲突，保持一致。

## 代码风格
- 兼容用户当前项目已有代码风格
- 先确认项目使用 JavaScript 还是 TypeScript、CSS 方案、路由方案、状态管理和包管理器，再做修改。
- 新增文件放到现有同类目录中，命名、导出方式、路径别名和组件拆分粒度保持一致。
- 不主动引入新框架、新 UI 库、新状态库或 React 兼容依赖；确实需要依赖时先说明原因。
- 只修改当前需求相关文件，不顺手调整无关格式、目录结构、依赖版本或视觉风格。
- 默认兼容桌面端和 iPhone 14 Plus；若用户指定严格复刻某个桌面原型，则参考视口下的像素一致性优先，禁止为移动端适配而改变桌面视觉。

## 组件与 JSX
- 优先使用函数组件，组件名使用 PascalCase，普通函数和变量使用 camelCase。
- hooks 从 `React/hooks` 引入；只有项目已经使用 signals 时，才从 `@React/signals` 或既有封装中继续沿用。
- 不使用 React 专属 API；需要兼容第三方 React 组件时，先确认项目已有 `React/compat` 配置。
- props、事件和状态命名要表达业务含义，不使用空泛缩写。
- 组件内部逻辑保持直接清晰；没有复用价值的代码不要抽成单独 hook 或工具函数。
- 多处重复且业务含义稳定的逻辑可以抽成同文件私有函数、hook 或项目已有工具模块。
- 每个页面的路由应该是不一样的  比如登陆页对应login

## 状态与副作用
- 组件本地状态优先使用 `useState`；跨组件状态沿用项目已有 store、context 或 signals。
- `useEffect` 只处理副作用，补齐依赖数组，并在订阅、定时器、请求竞态等场景中做好清理或失效保护。
- 能通过 props、state 或 signal 派生的值，优先直接派生；计算成本明显时再使用 `useMemo`。
- `useCallback` 只在能减少真实重复渲染、稳定依赖或满足子组件引用要求时使用。
- 表单优先使用清晰的受控或非受控模式，不混用导致状态来源不明。

## 视觉参考强制边界

- 用户指定 HTML、设计稿、截图、Figma、现有页面或组件作为视觉参考时，该参考是唯一视觉事实来源，其优先级高于行业惯例、模型审美、默认设计方案和移动端适配偏好。
- “严格参考”“严格按照”“像素级还原”“不要自己发挥”等表述触发零自由设计模式：禁止自行修改配色、字体、字号、间距、尺寸、圆角、阴影、渐变、布局比例、组件形态、图标、文案层级和信息密
  度。
- 将 HTML 原型转换为 React 时，只允许修改实现方式和状态绑定，不允许改变最终 DOM 的视觉结构和 CSS 表现。
- 开始编码前必须完整检查参考文件的 DOM、CSS 变量、布局尺寸、响应式规则和交互状态；不得只参考截图或局部结构后重新设计。
- 优先直接复用参考文件中的 CSS、CSS 变量、class 命名、SVG 图标和组件层级。新增 CSS 只能用于 React 状态绑定或参考文件未覆盖的必要交互，禁止覆盖参考文件已有选择器的视觉值。
- 参考文件未定义某个状态时，只能复用其中最接近的现有组件样式；如需引入新的视觉模式，必须先向用户说明差异并取得确认。
- 只有在用户没有提供任何设计稿、原型、截图、现有页面、组件库或项目样式时，才允许参考行业方案；使用行业方案前必须明确告知用户。
- 严格复刻桌面原型时，桌面端一致性优先于默认移动端适配规则。移动端样式必须放在隔离的 media query 中，且不得改变参考视口下的桌面表现；需要重新设计移动端结构时必须先取得用户确认。
- 完成后必须使用与参考相同的视口进行浏览器截图对照，检查布局比例、颜色、字体、间距和主要交互状态。
- 存在无法完全复刻的技术限制时，必须明确列出差异，不得自行选择替代设计并当作完成。

## 样式与交互
- 默认沿用项目已有样式方案，例如 CSS Modules、Tailwind、vanilla CSS、Sass 或组件库样式 API。
- 新增交互要覆盖 loading、disabled、empty、error 和可取消状态中与需求直接相关的部分。
- 保持移动端和桌面端都可用；固定格式元素使用稳定尺寸约束，避免 hover、图标、文案变化造成布局跳动。
- 文案放在已有国际化或常量体系中；项目没有对应体系时，直接写最小必要文案。
- 默认不做装饰性重设计，不新增与功能无关的动画、渐变或大面积配色变化。
- 单击选定输入框, 并且要有输入ui提示
- “查询中/操作中...”等接口请求状态使用模态浮层：明显遮罩、加载动画，并利用浏览器模态对话框在接口返回前阻止鼠标、触摸和键盘操作。
- 单一条件时, 无需再使用查询按钮, 而是用户完成查询条件后, 自动查询
- 日期 点击后, 要跳出日期选择的插件
- 悬浮提示应在鼠标移入后立即显示，不使用存在延迟的浏览器原生提示。
- 悬浮提示要足够大, 而不是小
- 用户触发的悬浮提示/用户点击后出现的新菜单/新窗口, 必须显示在页面最上层
- 悬浮工具栏显示后，用户选择其他位置时应立即关闭。
- UI设计要工整, 不要乱七八糟
- 除了用户明确指明的字号, 选择字号要足够大, 而不是小,

## 类型与数据
- TypeScript 项目中为 props、请求结果和关键状态补充明确类型；避免为方便绕过问题而使用 `any`。
- API 数据进入组件前要处理空值、默认值和字段缺失；不要让模板中堆积复杂兜底表达式。
- 事件处理函数先取出有业务含义的中间变量，再调用核心逻辑，避免把复杂表达式直接塞进参数。

## 测试与验证
- 不自动生成测试用例。如果用户要求写测试，保持测试逻辑简单，优先覆盖主流程、关键分支和明显边界。
- 修改完成后优先运行项目已有的类型检查、lint；找不到脚本时说明未验证原因。
- 新增依赖, 自动安装前端依赖
- 默认禁止自动构建校验和自动测试
- 使用 ip:port 进行真实测试, 桌面端使用 chrome 进行测试
- 如完成测试, 测试成功后, 把测试用例同步保存到 test 中
- 测试完后要 kill 掉相关进程

## 变更边界
- 不得擅自改变既有布局
- 除非用户要求参考行业内类似场景和功能的优秀方案和标准, 否则必须强制按照用户要求进行设计, 禁止修改无关代码和逻辑
- 生成的代码必须可直接落地，不写 TODO、伪代码或“示意实现”。
- 已存在的文件、代码和注释，除非与当前需求直接相关，禁止删除或重写。
- 与本次修改无关的文件/代码/注释, 禁止删除
- 禁止修改与用户当前需求无关的代码、配置占位符、注释、格式、命名、依赖、接口 URL、调度表达式等内容。即使发现现有代码看起来不够优雅、不够一致、可能有更好的写法，也只能在回复中提示，不得顺手修改。
- 新增代码时优先做最小必要改动，不顺手扩展范围，不主动重构整条链路
- 直接修改相关代码即可
- 严禁过度设计, 禁止引入完全用不到的字段/功能等

## 逻辑
+ 后端接口禁止使用各类 proxy 转发, 直接使用完整后端地址
+ 使用框架内已有的日志工具，在关键节点 加入 日志打印
- 在满足 `.gitignore` 的前提下, 每次代码增删改，必须使用 `git add .`、`git add -A`自动添加生成后的代码文件
